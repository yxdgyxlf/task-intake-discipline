# 任务接收纪律（Task Intake Discipline）

[English](README.en.md) | 中文

面向 AI Agent 的「会话开局任务接收与开工前置」协议——以常驻注入（强加载）方式部署，任何任务开始前自动生效。单文件协议，无脚本、无依赖。

> 核心主张：任务接收自有纪律——先静候、再判别、后开工；信息未齐不擅动，技能未检不开工。

## 解决的问题

1. **开局抢跑**——任务已至而指令、边界、产物要求未齐时即自行开工，用户被迫中途插队纠偏；本协议将「输入完成确认」设为硬性开工门槛。
2. **未作分流**——不同明晰度的任务缺少区分处置：明确的任务被多余环节打断、模糊的任务被自行脑补；本协议按四种开局情形分别处置。
3. **求援顺序颠倒**——遇阻时自行反复排查，而非直接向用户确认；本协议明确「询问优先于自查」。
4. **开工漏载**——任务适用的技能未被检索加载；本协议在开工闸门中内置技能检索，防漏载。
5. **流程空转**——确认与等待环节缺少出口，可能反复打转或无限等待；本协议以三条防空转设计保证每条路径都有终点。

## 工作机制

1. **四情形判别**：①任务、指令、边界三清 → 直接执行；②工作流成熟 → 直跑，不打断；③三无（无确认指令、无边界、无产物要求）→ 禁止自行启动，先确认；④任务与要求模糊 → 先确认。
2. **开工闸门（接收时序）**：只读静候（零动作、零检索）→ 补充指令至「输入完成」→ 预演方向 → 检索适用技能（防漏载）→ 「无新增需求」确认 → 开工。
3. **防空转三条款**：直通（①②免确认门）｜回流（新增需求回到收口，直至一轮无新增）｜无答复与无人值守（同一问题只问一次；无人值守按显式假设执行并标注）。
4. **强加载**：一经加载即进入强加载状态，任何任务开始前强制注入；适用于支持常驻注入的 Agent 系统（如 Hermes 的 `skills.auto_load` 全文注入机制）。
5. **范围克制**：确认门仅作用于用户在场的交互会话；自动化场景不套用——与既有功能互不影响。

## 与既有方案的关系

本技能不声称首创全部机制，如实说明与生态中既有方案的关系：

- **[Superpowers](https://github.com/obra/superpowers)**（编码 Agent 的开发方法论，社区头部技能框架）：已在「写代码」场景中实现开工前的澄清与设计确认硬门，并明确提出「会话启动必须加载引导（bootstrap），否则技能只是磁盘上的死重」；本项目与其互补——它管开发流程，本技能管会话开局的任务接收（不限任务类型），可共存。
- **ask-questions-if-underspecified 系**（同名技能被多家公开技能库收录，如 Trail of Bits）：验证了「信息不足先问、未齐不动工」是普遍共识；本技能将其扩展为完整的接收时序（静候 → 分流 → 闸门 → 防空转），并以常驻注入默认生效，而非仅在显式调用时使用。
- 生态先例说明：「会话启动注入」「开工前确认」等单项机制已有先例；本技能的独有部分是——四情形分流、开工闸门内置技能检索（防漏载）、确认环节防空转条款（直通/回流/无人值守）、以及作用范围声明。
- 诚实说明：本技能来自真实会话的实践沉淀（与 AI Agent 长期协作中逐条教训凝练），已完成本机部署验证；尚未建立自动化评测（eval）体系，欢迎以实践反馈与 issue 补充。

## 安装

- **Hermes Agent**：将 `SKILL.md` 放入技能目录，并列入常驻注入清单（`skills.auto_load`）——自下一个新会话起自动全文注入。
- **其他 Agent 系统**：将 `SKILL.md` 复制到对应技能目录即可按需加载；若系统支持会话启动注入/常驻注入（resident injection），建议列入常驻清单，以获得「开工前强制注入」的完整效果。

## 用法（三步）

1. **部署**：按上文将本技能放入技能目录（及常驻清单）。
2. **正常对话**：无需额外操作——任务到达时协议自动生效。
3. **校准**：若你的场景有特殊边界（如全自动流水线），参照协议内「作用范围声明」条款调整。

## 已知边界（诚实声明）

- 本技能是**协议文本**，不是可执行代码；效力取决于宿主系统的技能加载与注入机制。
- 沉淀自真实会话实践，尚无自动化评测；条款将随实践继续修订。
- 「会话启动注入」「开工前确认」等单项机制在生态中已有先例（见「与既有方案的关系」）；本技能的价值主张在组合与条款细节，不在单点首创。
